  1. Part A · Our work
  2. 1
    The problem

    A robot policy is trained at one speed but has to run at another

    A policy plans small movement steps at a fixed rate. If it must run slower (every k steps), it only sends one total per block of k steps. The robot's controller still needs every small step, so we have to rebuild them from the totals.

  3. 2
    The hidden trap

    Smooth curves overshoot the controller's limit, and the extra motion is thrown away

    The robot's controller only accepts commands between −1 and +1. Anything past that is silently cut. A smooth curve often bulges past the limit, so part of the motion the policy asked for never happens, and the robot drifts off its plan.

  4. 3
    Our method

    A "governor" that keeps the motion and respects the limit

    Instead of guessing a curve and fixing it later, we solve one small optimisation that follows three rules at once. It needs no training and no robot model, and runs in under a second per episode.

    Keep every block totalThe robot moves exactly as far as the policy asked. Nothing is lost.
    Never pass ±1The limit is part of the solution, so the controller has nothing to cut.
    Stay close to TAC-Fold's shapeIf TAC-Fold's own answer is already inside the limit, the result is identical to it.

    Name in code: qp_anchor. Where there is room, a block over the limit can borrow slack from its neighbour, which a one-block-at-a-time fix cannot do.

  7. 6
    Honest gaps

    Why it is not yet a strong positive paper

    • One task. Only PickCube has a significant live win, and the margin is small (+3.3 points).
    • Only compared with our own family. No outside method (such as RTC or low-pass filtering) has been run yet.
    • Rebuilding still costs a lot. The same policy at its original rate reaches about 90% on PickCube (n=100 run); every rebuilt version sits near 50%.
    • Not a real VLA test. The policies read robot state, not camera plus language. On teleop VLA benchmarks, actions rarely hit the limit, so no method shows an effect.
    • No written proofs yet. The "never makes a valid plan worse" property is argued, not proven on paper.

    Finding · by reading the code

    At k=4 every method rebuilds from only 2 numbers, and useful information is thrown away

    The policy predicts 16 steps but runs only the first 8. At k=4 that is just 2 totals, so all the rebuild methods end up almost the same, which explains why their live results barely differ. The policy's other predicted steps, and the chunk that just ran, are never used.

  11. 9
    Keeping it fair

    Tuning and proving happen on different episodes

    Trying many ideas and reporting only the one that won would be cheating. So each set of PickCube starting states has exactly one job:

    • Dev episodes pick the design. They decide which variant goes forward (context or not, ARC or not). They are never cited.
    • The plan is written before the test. A pre-registration fixes the tasks, methods and pass rule before confirmation runs start.
    • Confirmation is large and corrected. 400 episodes per task, exact McNemar, Holm correction.
    • Credit goes where it belongs. If context helps every method equally, the gain is reported as coming from context, not from our method.

  17. 14
    TAC-Fold · a formula

    TAC-Fold draws one smooth curve through the block edges

    1. Mark where the robot must be at each block edge. Add up the totals: 0 → 3.6 → 4.0 → 4.4 → 8.0 (black circles).
    2. Pick a slope at each edge. Akima's rule averages the two neighbouring blocks, giving less weight to the one that changes more. Middle edges get 0.1 per step. The two chunk ends have no neighbour, so the slope is extrapolated: 1.3 per step, already past the limit (orange ticks).
    3. Draw a smooth cubic through the edges with those slopes (teal curve). The dashed line is ZOH, straight between edges.
    4. Read the step sizes off the curve: each step = how far the curve rises in that step. Because the curve hits every edge exactly, every block total is exact.
  18. 15
    What the robot actually does

    The controller cuts everything past +1, and that motion is gone

  19. 16
    Satfix · a repair after the fact

    Satfix fixes each block on its own

    1. Clip every step past ±1.
    2. Hand the missing amount (0.4) to the steps in the same block that still have room.
    3. Repeat until the block total is exact again.
  20. 17
    The QP governor · an optimisation

    The QP solves all 16 steps at once, with the limit built in

    1. Unknowns: all 16 step sizes together, not one block at a time.
    2. Hard rule 1: each block adds up to its total exactly (3.6, 0.4, 0.4, 3.6).
    3. Hard rule 2: every step stays within −1 and +1.
    4. Preference: among all sequences that obey both rules, pick the one whose step-to-step changes are smallest (qp), or closest to TAC-Fold's changes (qp_anchor), or closest to the learned network's shape (qp_learned).
    5. A solver finds the best such sequence in about a millisecond.

  22. 19
    The identity question

    If the network alone scores the same, why keep the QP?

    The reviewer's questionThe learned network alone scored 66%; with the QP, 65%. Why not train the network to stay inside ±1 (for example with tanh) and drop the QP?

    1. Staying inside ±1 is not the same as delivering the commanded motion. tanh keeps every step under the limit, but nothing makes a block add up to what the slow policy commanded. The QP is the smallest change to the network's guess that achieves both at once.
    2. The QP only acts when the network overshoots. On PickCube the network's guess goes past ±1 on just 6.6% of values, so there is almost nothing to fix. That explains the 65 vs 66 tie. On RollBall it is 30%.
    3. It is a guarantee, not a hope. The true motion always obeys both rules. So the QP can never move the network's guess further from the truth, measured in step-to-step changes. When the network is wrong, the QP pulls it back toward what the policy asked for.

    One-line answer for the paper

    The network decides how to move inside a block; the QP guarantees how far. Bounding the network cannot give that guarantee.
